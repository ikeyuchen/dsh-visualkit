# CSS 层：能机械到哪一步

> 结论：**能机械化的只有「同一维度上的取值收敛」**；跨维度的判断（配色取向、层级策略、组件形态）不该自动化。每个候选动作都要带验收方式。

## 一、已实现的四个 action（`css_edit`）

| action | 收敛什么 | 为什么可约束 | 验收 |
|---|---|---|---|
| `snap` | `margin/padding/gap` → N px 网格 | 间距是一维的：只有大小，没有取向 | 网格合规率 + 渲染 diff 无位移 |
| `scale` | `font-size` → 给定阶梯 | 字号同样是一维的 | 字号档位数 + 渲染 diff |
| `leading` | `line-height` → 1.5/1.6/1.8，标题不动 | 行高也是一维的 | S3 剩余告警 + 渲染 diff |
| `radius` | `border-radius` → 2/4/8/12，带令牌化门槛 | 一维，但在令牌化项目上收益接近 0 | 圆角档位数（外观应不变） |

四个都只动**绝对值**：`var()/calc()/%/em/rem/auto` 一律跳过——实际尺寸由上下文决定，静态改数等于猜。

### `action=leading`：78 处实测选出的规则

4 个真实项目的 **78 处** line-height 声明，模拟三种规则：

| 规则 | 改动 | 归一后 S3 剩 |
|---|---|---|
| A 全部就近归并到 1.2/1.35/1.5/1.6/1.8 | 23% | **10 处（等于没改）** |
| **B 标题不动；正文死区抬到 1.5；≥1.5 就近归并 1.5/1.6/1.8** | 23% | **2 处** |
| C 同 B，但标题也归并到 1.1/1.2/1.3 | 36% | 2 处 |

**选 B**：A 失败的原因很具体——**1.35–1.5 正是 S3 的告警区**，归到 1.35 是从"没那么紧"变成"依然紧"；C 多改 56% 的声明却零收益。

实现边界（都写进了测试）：标题级**一律不动**（`h1–h6` / `.*title*` / `.*display*`，S3 本来就不判它们）；`<1.2`（大字号紧凑排版）、`>2.2`（松散排版）、`px` / `var()` / `normal` 全部保留；平局取大且比较带 `1e-9` 容差（浮点下 `|1.6-1.7|` 与 `|1.8-1.7|` 差在 1e-16 量级，严格 `<=` 会把 1.7 判到 1.6）。

### `action=radius`：令牌化率 ≥50% 时拒绝

| 项目 | 可改 px | **已是 var()** | 保留(%/0/999) |
|---|---|---|---|
| Colibri | 9 | **119** | 16 |
| Echo | 0 | **34** | 0 |
| Flow-Pilot | 1 | **7** | 0 |
| 旧版 0.5.4 | **124** | 0 | 47 |

三个现代项目的圆角早已令牌化，只有手写时代才是散落 px——在它们身上收敛散落 px，改完外观几乎不变，用户却以为统一了。所以实现有一道**门槛**：令牌化率 ≥50% 时直接拒绝，并指向正确做法（改 `:root` 的 `--radius-*`）。实测：Colibri 报「已令牌化 82%（119/146 用 var()）——要改就改 `:root` 的 `--radius-*` 值」；旧版源码 0/171 未令牌化（散落值 6px×36 4px×33 3px×28…），跑 `action=radius` 可改 11 处（border-radius 6px → 8px）。

对真需要收敛的项目才动手：阶梯 `2/4/8/12`，保留 `50%`（圆）/ `0`（无圆角）/ `≥100px`（胶囊）/ 单角属性与多值简写（拆开会丢语义）。

## 二、还没做的两个候选

| 候选 | 机械逻辑 | 判断 |
|---|---|---|
| 过渡时长/缓动（`transition` / `animation`） | `transition: X 180ms ease` 的时长收进 `120/160/240/320ms` 四档，判据来自 `design_style format=motion` 的 `--t-fast/base/slow`（同一条时间阶梯，这里反向归并） | 风险低（时长分歧对观感影响远小于圆角），但无法用静态体检验收，只能人看 |
| `z-index` 归一 | 扫数值重排成 `10/100/1000` 三档并保持相对顺序 | 收益低（问题罕见）、风险高（改错会破叠层），不建议做 |

## 三、明确不做（跨维度判断）

| 候选 | 为什么不做 |
|---|---|
| **色相家族收敛**（11 族 → 4 族） | 哪些颜色是"品牌色必须保留"、哪些是"随手加的高饱和色"，只有人知道。工具能**报**（`hue-sprawl`），不能改 |
| **配色取向**（冷暖、明度阶梯） | 设计决策，不是规范背离 |
| **组件形态**（卡片 vs 表格 vs 列表） | 信息结构问题，`layout_check` 只该报，不该动 |
| **阴影方向统一** | `S11` 能报"有上有下"，但哪边是"正确光源"取决于设计意图 |

共同点：这四项都在多个维度之间做取舍，而机械化的前提是「同一维度上取更接近的值」。

## 四、判断新动作该不该加

三个问题全部答"是"才做：① 只在一维上做归并（否 → 不做）② 改完能被现有工具验收（`layout_check` 规则或渲染 diff 拦得住）③ 默认值不替用户做风格决定（会 → 必须显式参数且默认关闭）。按这三条：`leading` 合格；`radius` 勉强（需显式开启）；过渡时长合格但只能人看；`z-index` 不合格。

## 五、实现约定

- **默认 dry-run**，`write=true` 才落盘；注释与字符串里的数字不动
- 平局取**大的**那档（往小缩会让中文变糊；Colibri 94 处里大半是 13px）
- 幂等：对齐过的再跑，改动数必须为 0
